## Behavior and interfaces

- **Behavior delivered:** Running `npm install` followed by `npm run verify` from the repository root executes, in order: (1) `tsc -b --force` across all three workspace packages via TypeScript project references (fails non-zero on any type error in any package), (2) `eslint .` across the whole repo (fails non-zero on any lint error), (3) `vitest run` across all `packages/*/src` test files (fails non-zero on any failing test; currently zero test files exist, which passes by design per the task brief's "empty test suite is acceptable at this stage" allowance, and does not silently skip the step — Vitest actually starts, discovers zero matching files, and exits 0 via `passWithNoTests: true`). The composite `verify` script uses `&&` chaining, so any earlier step's non-zero exit stops the chain and propagates the failure.
- **Interfaces consumed:** None (T-01 has no task dependencies).
- **Interfaces produced:**
  - `npm run verify` command contract: runs `tsc` (workspace-wide, strict), `eslint .`, `vitest run` (workspace-wide) in sequence, non-zero exit on any failure. This is the exact command every subsequent task (T-02–T-21) will use as its full-verification step.
  - npm workspaces structure: `@paritylens/shared`, `@paritylens/engine`, `@paritylens/extension`, each independently resolvable via the workspace protocol (`engine` and `extension` already declare `"@paritylens/shared": "*"` / `"@paritylens/engine": "*"` dependencies resolved by npm to the local workspace packages), each with its own `tsconfig.json` (strict, composite, TS project references) and its own placeholder `src/index.ts`.

## Assumptions and risks

- **Assumptions:**
  - The TASK-BRIEF.md's "focused" and "full" verification commands are identical (`npm run verify`) for T-01 specifically, as the brief itself states.
  - `tsc --noEmit` from the brief's prose is satisfied by `tsc -b --force` using TypeScript project references across the three composite packages (project-reference builds require `composite: true` and do not support a bare `--noEmit` flag in build mode; `-b` with declaration/sourceMap output to each package's `dist/` is the standard workspace-aware equivalent and still fails non-zero on any type error, which is the contract's actual requirement). `dist/` output is gitignored.
  - `.eslintrc.cjs`/`.eslintrc.json` were offered as options in TASK-BRIEF.md with "implementer's choice, record which" — I used `eslint.config.mjs` (ESLint 9 flat config) instead, since the installed ESLint major version (9.x, current stable) uses flat config by default and a legacy `.eslintrc.*` file would require `ESLINT_USE_FLAT_CONFIG=false` or a downgrade. Recording this substitution explicitly for reviewer awareness.
  - Because the repository had zero commits before this task, the pre-existing control documents (`AGENTS.md`, `PROJECT-BRIEF.md`, `DESIGN-SPEC.md`, `IMPLEMENTATION-PLAN.md`, `PROGRESS-LEDGER.md`, `TASK-BRIEF.md`, `Idea Prompt.md`, `multi-agent-idea-to-app/`) were included in this task's initial commit unmodified, since there was no other commit to attribute them to and leaving them permanently untracked was not a safe alternative. Their content was not read for editing purposes beyond what AGENTS.md/TASK-BRIEF.md/IMPLEMENTATION-PLAN.md required me to read, and none of their content was changed.
- **Risks or limitations:**
  - `npm audit` reports 10 vulnerabilities (1 critical, 6 high, 3 moderate) in transitive devDependencies only (`brace-expansion`/`minimatch` via ESLint's dependency chain; `esbuild` via Vite's dev server, used only by Vitest). All are dev-tooling-only, not shipped in the extension bundle or engine runtime, and fixing them requires breaking major-version upgrades (`eslint@10`, `vitest@4`) that are out of T-01's scope. Flagging for a future dependency-maintenance task rather than fixing here.
  - The Vitest suite currently has zero test files anywhere in the repo, which is explicitly acceptable per TASK-BRIEF.md's green-state definition, but means `vitest run`'s pass/fail signal is not yet exercised against a real failing test. T-02 onward will exercise this.
  - `tsc -b --force` was used instead of an incremental `tsc -b` to guarantee a clean, non-cached verification run for this report's evidence; the `verify`/`typecheck` script as committed always uses `--force`, so every `npm run verify` invocation does a full rebuild (slightly slower but never falsely green from stale `.tsbuildinfo` cache).
- **Blockers:** None.
